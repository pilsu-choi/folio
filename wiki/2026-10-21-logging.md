# 디버깅용 구조화 로그와 로그 저장

## 배경

OpenRouter로 testset을 만들 때 생성 단위 3개가 실패했지만 원인이 어디에도 남지 않았다([평가 작업 기록](./2026-10-21-eval-span-testset.md)). 라이브러리·API·worker·채팅 App 어디서든 원인을 볼 수 있게 로그를 정비하고, 로그를 어디에 저장할지 정했다.

## 결정

- **형식**: 한 줄에 JSON 하나. `ts`, `level`, `logger`, `event`, 필드들, 그리고 문맥에 있으면 `request_id`·`job_id`. 구현은 [folio/logging.py](../folio/logging.py) 하나(`configure`, `log_event`, `clip`, `redact_url`, `ms_since`, `with_context`).
- **대상 logger**: `folio`, `service`, `apps`만 설정하고 root logger는 건드리지 않는다. Airflow·노트북 같은 호스트의 로깅을 바꾸지 않기 위해서다.
- **레벨**: `FOLIO_LOG_LEVEL`, 기본 INFO. CLI는 `folio --log-level DEBUG <명령>`이고 하위 프로세스(worker, uvicorn)에도 같은 값을 넘긴다. 잘못된 값이면 INFO로 돌아간다.
  - INFO: 요청당 한 줄, job 시작·단계·완료, 채팅·eval 요약.
  - DEBUG: 외부 호출 상세와 잘린(`clip`) 사용자 내용. 장애 분석용이며 운영에서 상시로 켜지 않는다.
  - WARNING: 재시도, 대체 경로(VLM→OCR, 변환 실패, 구조 분석 실패 시 text layer), 실패한 생성 단위. ERROR: 최종 실패와 traceback.
- **비밀값**: API 키, Authorization 헤더, 쿠키, OIDC 토큰, `FOLIO_APP_SECRET_KEY`, URL·DSN 안의 `user:password@`는 어느 레벨에서도 남기지 않는다. 필터는 키만 남긴다(값이 tenant id일 수 있음).
- **요청 추적**: 채팅 App과 API 모두 `X-Request-ID`를 받거나 새로 만들고 응답 헤더로 돌려준다. App은 folio API 호출에 같은 id를 실어 보내므로 한 id로 App→API를 따라갈 수 있다. worker는 task 동안 `job_id`를 문맥에 둔다. ThreadPoolExecutor 안에서도 `with_context`로 유지된다.
- **출력 위치**: 로그는 stderr로 낸다. `eval testset` 같은 CLI 결과 JSON은 stdout에 그대로 남아 파이프로 쓸 수 있다. 컨테이너 런타임은 stdout과 stderr를 둘 다 수집한다.
- **access log**: `folio api`는 uvicorn access log를 끄고 미들웨어의 `http_request` 한 줄만 남긴다. `/healthz`·`/readyz`·정적 파일은 DEBUG. uvicorn 자체 로그(`uvicorn`, `uvicorn.error`)와 `celery` logger도 `adopt()`로 같은 JSON 핸들러를 쓴다. Compose·Helm의 api/worker는 모두 `folio api`·`folio worker`로 시작하므로(이미지 ENTRYPOINT `folio`) 이 설정이 적용된다.
- **Celery**: `setup_logging` 시그널에 연결해 Celery가 root logging을 설정하지 않게 하고, `celery` logger도 같은 JSON 핸들러를 쓴다. 레벨은 Celery `--loglevel`이 아니라 `FOLIO_LOG_LEVEL`을 따른다.

## 로그 저장

| 실행 환경 | 저장 방식 |
| --- | --- |
| Docker Compose | 모든 서비스(15개)에 `x-logging` 앵커: `local` 드라이버, `FOLIO_LOG_MAX_SIZE`(기본 20m) x `FOLIO_LOG_MAX_FILES`(기본 5). `docker compose logs -f api`로 조회 |
| Kubernetes(Helm) | 컨테이너 stdout/stderr를 kubelet이 로테이션(`containerLogMaxSize`). 보관·검색은 클러스터 수집기(Fluent Bit, Promtail/Alloy → Loki 등)에 맡긴다. 차트에 별도 수집기를 넣지 않았다 |
| 컨테이너 밖(CLI·노트북) | `FOLIO_LOG_FILE`을 주면 stderr와 함께 로테이션 파일에도 쓴다(`FOLIO_LOG_FILE_MAX_MB` 50, `FOLIO_LOG_FILE_BACKUPS` 5) |

앱 안에서 파일을 직접 쓰는 방식은 컨테이너에서 쓰지 않는다. 컨테이너는 `read_only`이고, 런타임과 클러스터 수집기가 로테이션·보관을 이미 맡기 때문이다.

## 주요 이벤트

| 영역 | 이벤트 (레벨) |
| --- | --- |
| HTTP 클라이언트(`post_json`) | `http_request`/`http_response` (DEBUG), `http_retry` (WARNING), `http_failed` (ERROR, 4xx는 응답 본문 300자) |
| LLM | `llm_reply` (DEBUG: finish_reason, usage, ms), `llm_truncated` (WARNING), `llm_bad_response` (ERROR, `choices` 없음 → FolioError) |
| testset | `testset_unit_failed` (WARNING: doc_ids, pages, types, 시도 번호, 원인), `testset_unit_reply` (DEBUG: 응답 500자), `testset_done` (INFO) |
| 파이프라인 | `stage` (INFO), `stage_start` (DEBUG), `stage_failed` (ERROR, traceback), `vlm_fallback`·`convert_fallback` (WARNING) |
| 검색·sink | `retrieve`, `rerank`, `sink_upsert` (DEBUG) |
| API | `http_request` (INFO), `http_error` (ERROR), `search`·`chat_request` (DEBUG), `chat` (INFO 요약), `search_rejected`·`chat_rejected`·`chat_failed` (WARNING) |
| worker | `job_start`, `job_stage`, `job_done` (INFO), `job_failed` (ERROR, traceback) |
| 채팅 App | `http_request` (INFO, 사용자는 email 대신 sub), `folio_call` (INFO/WARNING/ERROR), `login_start`·`login_success`·`logout` (INFO), `login_failed` (WARNING), `unhandled_exception` (ERROR) |

## testset 실패 원인 (실제 실행)

같은 설정(M1 공개 문서 16개, `--pages 10 --pairs 10 --min-per-type 3`, OpenRouter qwen/qwen3.8-27b, reasoning off)으로 `--log-level DEBUG` 실행:

- 생성 단위 36개 중 4개 실패, 시도 9번 모두 `JSON decode error: Expecting ',' delimiter`. 응답 길이 375~627자, 41개 호출 모두 `finish_reason=stop`이라 잘림이 아니었다.
- DEBUG 응답을 보니 모델이 바깥 배열의 닫는 `]`를 빠뜨렸다: `[{..., "evidence": [...]}`. 기존 파서는 정규식 `\[.*\]`로 안쪽 evidence 배열의 `]`까지만 잘라 실패했다.
- 수정: `_parse_items`가 `[` 위치마다 `raw_decode`로 읽고(뒤에 붙은 설명문 허용, `[1]` 같은 앞쪽 배열은 건너뜀), 실패하면 `]`를 하나 붙여 한 번 더 시도한다. 객체 배열이 없으면 실패로 기록하고 재시도한다.
- 수정 후 같은 설정으로 기본 INFO 실행: 단위 38개, **실패 0**, 8개 유형 모두 kept ≥ 3. stderr에는 `testset_done` 한 줄만 나왔다.
- DEBUG 로그 전체에서 OpenRouter 키 접두사(`sk-or`)는 0건이었다.

## 미검증·남은 일

- 실제 Celery worker 프로세스로 띄워 출력 형식을 보지는 않았다(브로커 필요). 다음 Compose E2E 때 `docker compose logs worker`로 확인한다. 채팅 App도 실제 프로세스로는 확인하지 않았다(TestClient만).
- OIDC 로그인 로그는 실제 IdP 없이 테스트하지 않았다.
- sink는 `upsert`에만 DEBUG 시간을 남겼고 search·delete는 없다.
- k8s 로그 수집기 구성은 클러스터 운영 쪽 결정으로 남겼다.
