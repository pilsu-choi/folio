# vlm_scan 정책 비교 (2026-10-21, 잠정)

스캔 페이지(이미지 경로)를 VLM으로 처리하는 방식 세 가지를 같은 샘플로 비교했다.

- `off`: OCR만(VLM 끔)
- `page`: 페이지 전체를 VLM에 보냄(기존 기본값)
- `ocr_first`: OCR 먼저, 표는 VLM으로 다시 읽고 그림은 VLM 설명을 덧붙임. OCR 신뢰도가 기준 미만이면 페이지 전체를 VLM으로 보냄(새 기본값)

## 설정

- DGX Spark(GB10, aarch64). OCR은 PP-StructureV3 CPU(이 장비에서 paddle GPU 불가), VLM은 Qwen3.5-9B bf16(vLLM 0.31, `gpu-memory-utilization 0.3`, 사고 모드 끔). 다른 세션의 `embed`·`rerank` 컨테이너는 그대로 떠 있었다.
- 샘플: 합성 스캔 s01~s10(텍스트 정답), 표 이미지 t01~t10(200dpi 렌더, 셀 정답; t01~t06 합성, t07~t10 실제 공정위 약관 표). 열화 없는 표 이미지라 실제 스캔 표보다 쉽다.
- 지표: 스캔은 정답 줄과 출력 전체 텍스트의 difflib 유사도(`run_manifest.py`와 같은 식), 표는 `scripts/bench_backends.py`의 `table_scores` 셀 정확도.
- 그림 설명은 정답 원문에 없는 문장을 더하므로 유사도를 깎는다. 그래서 그림 블록을 뺀 유사도도 함께 낸다.
- `ocr_first`는 `ocr_min_conf=0`으로 한 번 돌려 페이지별 OCR 신뢰도를 기록했다. 다른 기준값은 `page` 결과와 합쳐 계산했다(`summarize.py`). 표의 `off`·`ocr_first`는 그림 설명 수정 후 재측정(`out/vlm_scan2`)이고, `page`는 첫 측정(`out/vlm_scan`)이다.

명령:

```
cd ~/folio-m1-bench/folio-scan
flock ~/folio-m1-bench/gpu.lock bench/m1/vlm_scan/run_all.sh                       # off, ocr_first, page
OUT=~/folio-m1-bench/out/vlm_scan2 POLICIES="off ocr_first" flock ~/folio-m1-bench/gpu.lock bench/m1/vlm_scan/run_all.sh
python bench/m1/vlm_scan/summarize.py out/vlm_scan2 out/vlm_scan
```

## 해석

- **본문 텍스트는 OCR과 같은 수준이다.** 그림 블록을 빼면 `ocr_first` 0.882, OCR만 0.888이다. 차이는 스캔 안의 표를 VLM이 다시 읽은 영향이다(s02).
- **`page`는 샘플마다 결과가 크게 갈린다.** s03·s04·s10은 OCR보다 높지만 s02(0.656)·s05(0.759)·s07(0.540)은 크게 낮다. 디버그 재실행에서 s02는 VLM이 표 내용을 다른 순서로 적었고, s05는 정답보다 60% 긴 텍스트를 냈다(반복은 아님). 파이프 기호를 빼고 다시 재도 점수는 거의 같았다(s02 0.659→0.667). 모든 블록의 bbox가 페이지 전체라 원문 위치도 잃는다.
- **표는 VLM으로 다시 읽는 효과가 크다.** 실제 약관 표 t07~t10은 OCR만 쓰면 0.28~0.33이고 `ocr_first`는 0.46~0.92다. 병합 셀이 있는 합성 표 t04는 VLM 파이프 표가 병합 셀을 표현하지 못해 0.667로 떨어졌다(`page`는 1.0). HTML 표 파서가 필요하다는 기존 과제와 같은 원인이다.
- **OCR 신뢰도는 기준값으로 쓸 신호가 없었다.** 스캔 10장이 모두 0.926~0.971이었고, 어느 정책이 이기는지와 관계가 없었다. 기준을 올리면 시간만 늘고 점수는 좋아지지 않는다. 기본값 0.85는 아주 나쁜 스캔만 걸러내는 안전장치로 두었다. 이 샘플에서는 한 번도 걸리지 않았고, 실제 저품질 스캔(r01~r04 같은)에서 동작하는지는 확인하지 않았다.
- **그림 설명은 원래 지표로 손해로 보인다.** s09는 0.686→0.338이다. 설명 문장이 정답에 없기 때문이며, 검색 품질 영향은 따로 재지 않았다.

## 측정 중 고친 것

- VLM 그림 설명이 그림 영역 안에서 이미 읽은 OCR·텍스트 레이어 글자를 덮어썼다. 표가 그림으로 잡힌 s03은 표 글자가 영어 설명으로 바뀌어 0.858→0.529가 됐다. 이제 원래 글자를 두고 설명을 뒤에 붙인다(디지털 페이지 경로도 같은 코드).
- 그림 설명 지시문이 영어라 한글 문서에서도 영어 설명이 나왔다. 그림 안 글자의 언어로 쓰라고 지시를 바꿨다.

## 남은 것

- t08(실제 표)이 어느 정책에서도 0.5 안팎인 원인.
- 저품질 실제 스캔에서 `ocr_min_conf` 동작 확인.
- 그림 설명이 검색에 주는 효과(청킹·검색 Eval).
- PP GPU가 되는 x86 장비에서 속도 재측정. 이 결과의 OCR 시간은 CPU 기준이다.
